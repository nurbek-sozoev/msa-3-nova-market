### **Название задачи:** Просмотр истории покупок
### **Автор:** Нурбек Созоев
### **Дата:** 2026-10-24
### **Функциональные требования**

|**N**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Покупатель | Просмотр списка заказов | Покупатель открывает личный кабинет и видит все заказы: стоимость, дату, способ доставки. |
| 2 | Покупатель | Просмотр деталей заказа | Покупатель открывает заказ и видит список товаров, количество, цену, итоговую сумму, способ доставки и оплаты, финальный статус. |
| 3 | Покупатель | Скачивание чека | Покупатель скачивает чек по завершённому заказу. |
| 4 | Покупатель | Отзыв о товаре | Покупатель оставляет отзыв о товаре из завершённого заказа. |
| 5 | Покупатель | Повторный заказ | Покупатель заказывает товары из предыдущего заказа повторно. |

### **Нефункциональные требования**

|**N**|**Требование**|
| :-: | :- |
| 1 | Время отклика интерфейса истории покупок сопоставимо с откликом остальных страниц приложения. |
| 2 | Чтение истории покупок не создаёт нагрузку на сервисы, участвующие в оформлении заказа. |
| 3 | Данные истории покупок доступны для чтения при временной недоступности отдельных сервисов. |

### **Решение**

Применён паттерн CQRS. В архитектуру добавлен Purchase History Service с собственной базой данных, которая хранит денормализованную read-модель истории покупок.

Purchase History Service подписывается на 5 событий из брокера сообщений:

| Событие | Данные для read-модели |
|---|---|
| OrderCreated | Состав заказа: товары, количество, цены, итоговая сумма, дата, способ доставки, способ оплаты. |
| PaymentSucceeded | Подтверждение оплаты, данные для формирования чека. |
| DeliveryRequested | Трек-номер, данные логистической службы. |
| OrderConfirmed | Финальный статус "подтверждён". |
| OrderCancelled | Финальный статус "отменён". |

При получении каждого события сервис обновляет запись в read-модели. Покупатель читает данные из одной базы без обращения к другим сервисам.

Логика выбора CQRS:

1. Сценарий "Просмотр истории покупок" требует агрегации данных из четырёх сервисов: Order, Payment, Delivery, Catalog.
2. Нефункциональное требование к отклику исключает синхронный опрос нескольких сервисов при каждом запросе.
3. В архитектуре из задания 1 уже реализована событийная модель. Purchase History Service подписывается на существующие события без изменения write-стороны.
4. Read-модель доступна для чтения при временной недоступности Order, Payment или Delivery Service.

### **Альтернативы**

**API Composition.** Отдельный сервис (или API Gateway) при каждом запросе обращается к Order, Payment, Delivery и Catalog Service, собирает ответы и возвращает агрегированный результат.

Преимущества:
- Данные всегда актуальны на момент запроса.
- Нет дополнительной базы данных.
- Проще в реализации: нет подписки на события, нет обработки проекций.

Недостатки:
- Время отклика определяется самым медленным из четырёх сервисов.
- При недоступности любого сервиса страница истории покупок возвращает ошибку.
- Каждый запрос на чтение создаёт нагрузку на write-сервисы.

**Event Sourcing.** Состояние каждого заказа восстанавливается из полной цепочки событий. Вместо хранения текущего состояния хранится журнал событий.

Преимущества:
- Полная аудируемость: можно восстановить состояние заказа на любой момент времени.
- Естественная совместимость с событийной архитектурой.

Недостатки:
- Не решает задачу агрегации данных из нескольких сервисов без дополнительной read-модели (CQRS поверх Event Sourcing).
- Восстановление состояния из цепочки событий медленнее прямого чтения из базы.
- Сложность реализации: версионирование событий, снапшоты, миграции формата событий.

**Недостатки, ограничения, риски**

1. Eventual consistency. Между публикацией события и обновлением read-модели проходит время. Покупатель может не увидеть только что оформленный заказ в истории. На практике задержка составляет секунды, что допустимо для сценария просмотра истории.
2. Дублирование данных. Read-модель хранит копию данных из других сервисов. При изменении формата событий нужно обновить проекцию в Purchase History Service.
3. Дополнительная инфраструктура. Отдельный сервис и база данных увеличивают стоимость эксплуатации.
4. Обработка событий "не по порядку". При сбоях брокера события могут прийти в другом порядке. Purchase History Service должен корректно обрабатывать ситуацию, когда PaymentSucceeded приходит раньше OrderCreated.
