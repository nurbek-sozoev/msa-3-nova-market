# Задание 4. Повышение надёжности приложения

## Часть 1. Rate Limiter

Конфигурация: [rate-limiter.conf](./rate-limiter.conf)

Исходный конфиг использовал одну зону `one` с лимитом 100 r/s для всех клиентов через общий location `/api/`.

Изменения:

- Создано две зоны rate limit: `web` и `mobile`. Каждая зона ограничивает запросы по IP-адресу клиента.
- Общий location `/api/` разделён на `/api/web/` и `/api/mobile/`. Каждый location использует свою зону.
- Параметр `burst` задаёт допустимый всплеск запросов сверх лимита: 100 для веб, 60 для мобильного приложения.

## Часть 2. Circuit Breaker

Конфигурация: [circuit-breaker.conf](./circuit-breaker.conf)

Исходный конфиг использовал таймауты по 30 секунд без обработки отказов.

Изменения:

- Таймауты `proxy_connect_timeout`, `proxy_read_timeout` и `proxy_send_timeout` снижены до 3 секунд.
- В upstream добавлены параметры `max_fails=5` и `fail_timeout=30s`. После 5 неудачных запросов подряд NGINX перестаёт отправлять запросы на сервер логистики на 30 секунд. По истечении паузы NGINX отправляет пробный запрос. Если сервер отвечает, вызовы восстанавливаются.
- Директива `proxy_next_upstream` определяет, какие ошибки считаются неудачными, это сетевые ошибки, таймауты, коды 502, 503, 504.
- При недоступности сервиса запрос перенаправляется в `@fallback`, который возвращает код 503 с JSON-сообщением.
